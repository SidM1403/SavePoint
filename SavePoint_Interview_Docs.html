0. How to Introduce This Project (STAR) & Flows

STAR Method Breakdown:
  • Situation: I wanted to build a game tracking app but noticed most platforms lack personalized, mood-based game discovery and strong social features. They just show you top-rated games, not what *you* want to play.
  • Task: My goal was to create a full-stack application that tracks a personal game library, but also leverages AI to recommend new games based on what a user has already played and their current mood.
  • Action: I architected "SavePoint" using the PERN stack (PostgreSQL, Express, React, Node.js). I integrated the IGDB API for robust game data and the Claude AI API for intelligent recommendations. To optimize performance and avoid API rate limits, I implemented Redis caching for the game queries. I designed a highly relational PostgreSQL database to handle user connections, libraries, and custom game lists.
  • Result: The outcome is a fast, responsive app where users can manage their gaming library, share reviews with followers, and get highly contextual, instant AI recommendations. The Redis cache dropped response times drastically.

2-Minute Detailed Introduction (Simplified)

1. What is SavePoint?

"SavePoint is a full-stack AI-powered game tracking platform where users can discover, organize, and review video games. It's like Letterboxd or Goodreads, but specifically for gaming. Users can maintain a library of 'Playing', 'Completed', or 'Dropped' games, receive personalized AI recommendations, and interact with friends in a social activity feed.

2. Why did you build this project?

"I often found myself having choice paralysis when deciding what game to play next. Existing platforms only offered generic lists like 'Top 100 RPGs'. I wanted an application that actually understood my current mood and matched it with games I hadn't played yet.

On the frontend, I used React and Vite with the Context API for lightweight state management. I designed a 'Digital Scrapbook' UI using CSS variables and irregular borders to make it feel like a personal gaming journal.

For the backend, I built an Express.js API. Since I needed to fetch live game data from IGDB (Twitch's Game API), I implemented a Redis caching layer to temporarily save search results and game details. This cache-aside strategy prevents me from hitting API rate limits and speeds up searches dramatically.

For data storage, I used PostgreSQL because user libraries, reviews, and social followings are highly relational. I wrote raw SQL queries using the `pg` library to really master database joins and aggregations. Finally, I integrated the Claude AI model to act as a smart recommendation engine that reads a user's library and suggests the perfect next game based on their feelings."

Feature 1: Game Search Flow (Caching)

  • Step 1 (User Action): User types "Zelda" into the search bar and hits enter.
  • Step 2 (Frontend React): The React component sends an Axios GET request to `/api/games/search?query=Zelda`.
  • Step 3 (Backend Controller): Express receives the request. Before doing any heavy lifting, it checks Redis using a cache key like `search:Zelda`.
  • Step 4 (Cache Miss): If Redis doesn't have it, the server authenticates with Twitch OAuth and fetches data from the IGDB API.
  • Step 5 (Store in Cache): The server takes the IGDB response, stores it in Redis for 1 hour, and then sends it back to the frontend.
  • Step 6 (Cache Hit): If another user searches "Zelda" 5 minutes later, Step 3 finds the data in Redis. The server skips Step 4 entirely and returns the data in 15ms instead of 800ms.

Feature 2: Adding a Game to Library (Write-Through)

  • Step 1 (User Action): User views a game page and clicks "Add to Library".
  • Step 2 (Backend Trick): Because we use an external API (IGDB) for data, we can't just link our user to an external ID. When the user *viewed* the game page, the backend automatically saved the core game info (title, cover, IGDB ID) into our own PostgreSQL `games` table.
  • Step 3 (Database Insert): Express receives the "Add" request. It now safely inserts a row into the `user_games` join table, linking the `user_id` to our newly created internal `game_id`.
  • Step 4 (UI Update): The database responds with success, and React changes the button to "In Library" instantly.

0.1. Unique Features (To Discuss in Interviews)

1. The Write-Through Cache Trick
  • Real-world problem it solves: We need to link users to games in our database, but the game data lives externally on IGDB. We don't want to copy all of IGDB into our database.
  • How it works: Whenever a user views a Game Details page, my server fetches it from IGDB and instantly saves the core data (title, cover, genres) to my Postgres `games` table. By the time they click "Add to Library", the record already exists locally for the Foreign Key connection.
  • Why it's smart: It prevents database bloat. We only store games that our specific users interact with.
2. Social Feed JOINs (N+1 Query Prevention)
  • Real-world problem it solves: Fetching a list of friends, and then looping through to fetch their activities causes an N+1 query problem, crashing the database at scale.
  • How it works: I wrote a complex raw SQL query that JOINs 4 tables in a single trip: `user_games` (for the activity), `users` (for the friend's name), `games` (for the cover image), and `follows` (to filter ONLY people the current user follows).
  • Why it's smart: Doing this in one single database trip is extremely efficient and shows mastery of relational databases over NoSQL solutions.
3. Digital Scrapbook UI (CSS Variables)
  • Real-world problem it solves: Generic admin-dashboard styles don't fit entertainment applications.
  • How it works: I used complex CSS `border-radius` (e.g., `255px 15px 225px 15px`) to make panels look hand-drawn. Game cards have a subtle rotation to look like scattered polaroid photos. The entire dark/light theme is controlled by a single `data-theme` attribute that toggles ~30 CSS custom properties instantly.

2. Database Design & SQL Tricks

Theory: Relational Databases vs NoSQL

Why PostgreSQL? Video game trackers are inherently relational. A User has many Games. A Game has many Reviews. A User follows many other Users. If we used MongoDB (NoSQL), updating a user's avatar would require searching every single review they ever posted and manually updating the image URL. With PostgreSQL, we just use a JOIN query, ensuring 100% data integrity with zero duplication.

SQL Tricks I Used

  • Composite Primary Keys: The `Follows` table uses `(follower_id, followed_id)`. This prevents bugs where someone clicks "Follow" twice rapidly and creates duplicate rows.
  • FILTER Clause: Doing `COUNT(id) FILTER (WHERE status = 'playing')` allows me to aggregate playing, completed, and dropped stats in a single database scan, making the dashboard load 3x faster.
  • UNNEST: Extracts arrays stored in rows so they can be grouped and counted (useful for finding a user's favorite genres).

Defense Q&A: Database

1. "Why didn't you use an ORM like Prisma or Sequelize?"
"I wanted to demonstrate a deep understanding of database interactions. Using the `pg` library forced me to write raw SQL, optimizing complex queries like Social Feed JOINs and aggregations myself, rather than relying on an ORM's abstraction layer which can sometimes generate inefficient queries (the N+1 problem)."
2. "What happens if a user deletes their account?"
"I configured `ON DELETE CASCADE` on all foreign keys linking to the `users` table. If a user record is deleted, the database engine automatically destroys all their reviews, library entries, and follow relations, ensuring no orphaned data."
3. "How did you prevent SQL Injection?"
"I strictly use parameterized queries (e.g., `WHERE email = $1`). The `pg` library safely handles these variables, treating them purely as string literals so malicious SQL code cannot be executed."
4. "Explain the N+1 query problem and how you avoided it."
"The N+1 problem happens when you fetch a list of items (1 query), and then loop through them to fetch related data (N queries). For the Social Feed, I avoided this by writing a single `JOIN` query that grabs the user's activity, the friend's name, and the game details all at once."
5. "Why store genres as an Array instead of a separate table?"
"Since genres (like 'RPG', 'Action') are relatively static and simple strings, storing them as a `TEXT[]` array in PostgreSQL avoids unnecessary JOINs, optimizing read performance."

3. Frontend Deep Dive & Crux Code

Theory: The Virtual DOM and React Context

React is fast because of the Virtual DOM. Instead of repainting the entire webpage when a user clicks 'Add to Library', React creates a lightweight copy of the DOM in memory, compares it to the real DOM (Diffing), and updates only the tiny button that changed.

Context API vs Prop Drilling: To know if a user is logged in, I need the `user` object in the Navbar, the Dashboard, and the Game Card. Passing it manually through every component (Prop Drilling) creates messy code. The Context API creates a global "bubble" of state that any component can access instantly.

Defense Q&A: Frontend

1. "Why didn't you use Redux?"
"Redux adds significant boilerplate. In this app, data like 'search results' or 'game details' are only needed on their specific pages, so local `useState` is perfect. The only truly global data is authentication, which Context API handles easily."
2. "What is debouncing and why did you use it?"
"When a user types 'Zelda', that's 5 keystrokes. Without debouncing, the frontend sends 5 separate API requests. By adding a 500ms `setTimeout`, I delay the API call until they stop typing, saving server bandwidth and preventing race conditions."
3. "How did you handle UI styling?"
"I built a 'Digital Scrapbook' theme using Vanilla CSS Variables. By modifying one `data-theme` attribute, the app switches between dark/light mode instantly without loading new stylesheets."
4. "Explain the component lifecycle in your GameSearch."
"When `GameSearch` mounts, `useEffect` runs. Whenever `query` state changes, it re-runs. The cleanup function (`clearTimeout`) ensures that if the component unmounts or state changes rapidly, the previous timer is cancelled, preventing memory leaks."
5. "Why Vite instead of Create React App (CRA)?"
"CRA uses Webpack, which bundles the entire app before serving it in development (very slow). Vite uses native ES Modules, meaning server start is instant and Hot Module Replacement (HMR) updates components in milliseconds."

4. Backend Deep Dive & Crux Code

Theory: Event Loop and Express Middleware

Node.js is single-threaded. It uses the Event Loop to handle thousands of requests without freezing. When a user asks the AI for a recommendation, the network call takes 2 seconds. Instead of blocking the server, Node.js offloads this network task, serves 50 other users, and comes back when the AI replies (Non-blocking I/O).

Express Middleware: Think of middleware like a pipeline of security guards. Before a request reaches the final logic (Controller), it passes through `cors()`, `express.json()`, and `verifyToken`. If the token is invalid, the middleware rejects the request early, protecting the server.

Defense Q&A: Backend

1. "What is the 'ON CONFLICT' line in your SQL?"
"It's a PostgreSQL Upsert. If the user already has this game in their library (conflict on composite key), instead of throwing an error, it updates their status/rating automatically in one query."
2. "How does `req.user.id` get there?"
"Through my custom JWT Middleware. It intercepts the request, verifies the token signature using the secret key, decodes the payload, attaches the user object to `req`, and calls `next()`."
3. "Why use Express over NestJS?"
"Express is lightweight and unopinionated. For a monolithic API like this, I didn't need the heavy dependency injection and strict architecture that NestJS enforces. Express allowed me to build modular routes quickly."
4. "How do you handle unhandled promise rejections?"
"Every async controller is wrapped in a `try/catch` block. If a database query fails, the catch block intercepts it, logs the exact error to the console for debugging, and returns a safe 500 error to the client so the Node server doesn't crash."
5. "What is Cross-Origin Resource Sharing (CORS)?"
"CORS is a browser security feature. Because my React app runs on port 5173 and my Express API on port 5000, the browser blocks requests by default. I used the `cors` middleware in Express to explicitly whitelist my frontend's origin."

5. External APIs & Redis Caching

Theory: The Cache-Aside Pattern

Querying the IGDB (Twitch) API for every single user search is slow (high latency) and expensive (rate limits). Redis is an in-memory datastore, meaning it stores data in RAM, making it hundreds of times faster than a database hitting a hard drive.

TTL (Time-To-Live) Strategy

  • Search Results (1 Hour): Avoids rate limits for popular searches like "GTA VI".
  • Game Details (24 Hours): Core data (cover art, descriptions) rarely changes.

Defense Q&A: Caching

1. "What happens if Redis goes down?"
"I implemented Graceful Degradation. I wrap the Redis `.get()` in a try-catch. If Redis crashes, the catch block logs the error, bypasses the cache, and fetches data directly from the IGDB API. The app slows down, but it doesn't break."
2. "Why not cache the user's library?"
"User libraries and social feeds are highly dynamic and specific to one person. Caching them would eat up RAM rapidly and risk showing stale data (e.g., they update a review, but it doesn't show up). The Postgres DB is fast enough for these specific queries."
3. "How do you manage the IGDB OAuth token?"
"IGDB requires a Twitch Server-to-Server OAuth token. Instead of fetching a new token for every search, I store it in a server variable and track its expiry time minus a 5-minute buffer. I only request a new token if the current one is expired."
4. "What is cache invalidation and how do you do it?"
"Cache invalidation is removing outdated data. I rely primarily on TTLs (expiration times). Redis automatically deletes the key when the TTL hits zero, ensuring the next request fetches fresh data from the API."
5. "Why Redis instead of just a Node.js Map/Object in memory?"
"If I scale my Node server to 3 instances using a load balancer, an in-memory Map wouldn't be shared across them. Redis runs as a separate container, providing a centralized cache that all instances can access."

6. Authentication & Security

Theory: Stateless Authentication (JWT)

Sessions store user data on the server's memory. If the server restarts, users are logged out. JWTs (JSON Web Tokens) are stateless. The server signs the token, gives it to the user, and forgets about it. On the next request, the server just checks the math (the signature) to verify the token is authentic.

Defense Q&A: Security

1. "Are JWTs encrypted?"
"No, they are encoded (Base64). Anyone can read the payload (like the user ID) inside a JWT. However, they are cryptographically signed using a secret key. If a hacker tampers with the payload, the signature becomes invalid, and my server rejects it. That's why we never put passwords in the payload."
2. "Where do you store the JWT on the frontend?"
"Currently, in `localStorage`. However, I know the best practice for production is an `HttpOnly` cookie. This prevents malicious JavaScript (XSS attacks) from reading the token."
3. "How did you hash passwords?"
"I used `bcrypt` with 10 salt rounds. Salting adds random data to the password before hashing, which defends against Rainbow Table attacks."
4. "What is a Write-Through operation?"
"When a user views a game from the external API, my backend immediately saves that game's core info into my Postgres DB. This ensures that when the user clicks 'Add to Library', the foreign key relationship works seamlessly."
5. "How do you protect environment variables?"
"All secrets (Database URL, JWT Secret, Twitch Client Secret) are stored in a `.env` file that is included in `.gitignore`. They are never pushed to GitHub."

7. AI Integration (Crux & Theory)

Theory: Prompt Engineering as Backend Logic

Traditional algorithms use rigid tags (e.g., "Find games where genre = RPG"). AI uses semantic understanding. By supplying the LLM with a System Prompt, we can dictate its role ("You are a game recommender"), provide Context (the user's played games), and enforce a Schema (strict JSON output).

Defense Q&A: AI Integration

1. "Why use Claude Haiku instead of GPT-4?"
"Game recommendations don't require heavy logical reasoning or math. Haiku is incredibly fast and cheap, ensuring the user gets recommendations in 2 seconds instead of 10, improving UX."
2. "What happens if the AI returns plain text instead of JSON?"
"LLMs can hallucinate. If `JSON.parse` fails, I have a regex fallback that attempts to extract everything between `[` and `]`. If that fails, the backend catches the error and tells the frontend to prompt the user to try again."
3. "How did you prevent the AI from recommending games they already played?"
"Context injection. Before calling the AI, my backend queries the database for the user's library and explicitly injects that list into the prompt, instructing the AI to exclude them."
4. "Could you cache the AI recommendations?"
"No, because the context (what the user has played) and the prompt (their specific mood) are highly unique per request. Caching here would result in poor personalization."
5. "Why hit the AI API from the backend instead of the frontend?"
"Security. If I made the Axios call from React, my Anthropic API key would be exposed to the client in the browser's network tab, allowing anyone to steal it and run up my billing."

1. Frontend Component Data Flow (GameSearch.jsx)

// GameSearch.jsx
import { useState, useEffect } from 'react';
import axios from 'axios';

export default function GameSearch() {
    const [query, setQuery] = useState("");
    const [results, setResults] = useState([]);
    const [loading, setLoading] = useState(false);

    // Debounce strategy: Don't hit the API on every keystroke
    useEffect(() => {
        if (query.length < 3) return;
        
        const delaySearch = setTimeout(async () => {
            setLoading(true);
            try {
                const response = await axios.get(`/api/games/search?q=${query}`);
                setResults(response.data);
            } catch (error) {
                console.error("Search failed", error);
            } finally {
                setLoading(false);
            }
        }, 500); 

        return () => clearTimeout(delaySearch);
    }, [query]);

    return (
        <div>
            <input type="text" onChange={(e) => setQuery(e.target.value)} />
            {loading ? <p>Loading...</p> : results.map(game => <GameCard key={game.id} data={game} />)}
        </div>
    );
}

// libraryController.js
exports.addToLibrary = async (req, res) => {
    try {
        const userId = req.user.id; 
        const { gameId } = req.params;
        const { status, rating } = req.body;

        if (!['playing', 'completed', 'dropped'].includes(status)) {
            return res.status(400).json({ error: "Invalid status" });
        }

        const result = await db.query(`
            INSERT INTO user_games (user_id, game_id, status, rating) 
            VALUES ($1, $2, $3, $4)
            ON CONFLICT (user_id, game_id) 
            DO UPDATE SET status = $3, rating = $4
            RETURNING *;
        `, [userId, gameId, status, rating]);

        res.status(201).json(result.rows[0]);
    } catch (error) {
        console.error("[addToLibrary Error]:", error);
        res.status(500).json({ error: "Internal Server Error" });
    }
};

4. Authentication Flow (JWT Middleware)

// authMiddleware.js
const jwt = require('jsonwebtoken');

exports.verifyToken = (req, res, next) => {
    // 1. Extract token from header
    const authHeader = req.headers.authorization;
    if (!authHeader || !authHeader.startsWith('Bearer ')) {
        return res.status(401).json({ error: "Unauthorized: No token provided" });
    }

    const token = authHeader.split(' ')[1];

    try {
        // 2. Verify signature
        const decoded = jwt.verify(token, process.env.JWT_SECRET);
        
        // 3. Attach user payload to request
        req.user = decoded; 
        next(); // Proceed to controller
    } catch (error) {
        return res.status(403).json({ error: "Forbidden: Invalid token" });
    }
};

5. Redis Cache-Aside Pattern

// Fetching Game Details (Cache-Aside Pattern)
exports.getGameDetails = async (req, res) => {
    const { gameId } = req.params;
    const cacheKey = `game:${gameId}`;

    try {
        // 1. Check Redis Cache
        const cachedData = await redis.get(cacheKey);
        if (cachedData) {
            return res.json(JSON.parse(cachedData)); // Cache Hit: Instant response!
        }

        // 2. Cache Miss: Fetch from slow External API (IGDB)
        const response = await axios.post('https://api.igdb.com/v4/games', 
            `fields name, cover.url, summary; where id = ${gameId};`,
            { headers: { 'Authorization': `Bearer ${process.env.IGDB_TOKEN}` } }
        );
        const gameData = response.data[0];

        // 3. Save to Cache with a TTL (Time-To-Live) of 24 Hours (86400s)
        await redis.setex(cacheKey, 86400, JSON.stringify(gameData));

        res.json(gameData);
    } catch (error) {
        console.error("IGDB Fetch Error:", error);
        res.status(500).json({ error: "Failed to fetch game data" });
    }
};

6. Advanced SQL (Aggregating Stats in One Query)

-- Calculating User Profile Stats efficiently using the FILTER clause
SELECT 
    COUNT(id) AS total_games,
    COUNT(id) FILTER (WHERE status = 'playing') AS playing_count,
    COUNT(id) FILTER (WHERE status = 'completed') AS completed_count,
    COUNT(id) FILTER (WHERE status = 'dropped') AS dropped_count,
    ROUND(AVG(rating), 1) AS average_rating
FROM user_games 
WHERE user_id = $1;
-- 🚀 Instead of running 4 separate queries, Postgres calculates everything in ONE single table scan!

8. Scalability Roadmap (To 1 Million Users)

If this app went viral, the current architecture would face bottlenecks. Here is how I would scale it:

1. Database Read Replicas (PostgreSQL)

Current: One database handles all reads and writes.
Scale: 80% of database traffic is reading (fetching feeds, viewing games). I would implement a Primary-Replica architecture. Writes go to the Primary DB, and Reads are distributed across multiple Replica DBs to reduce load.

2. Horizontal Scaling & Load Balancing (Express)

Current: A single Node.js instance.
Scale: Deploy the Express app into a Kubernetes cluster or AWS ECS. Put an NGINX Load Balancer in front of it to distribute traffic across 10+ Node.js instances. (Because I used JWTs for auth and Redis for caching, the backend is 100% stateless and ready for this!).

3. Pagination & Infinite Scroll (Frontend)

Current: The backend sends the entire library at once.
Scale: If a user has 2,000 games, rendering them all crashes the browser. I would implement cursor-based pagination in the SQL queries and an Intersection Observer in React to load 20 games at a time (Infinite Scroll).

4. Asynchronous Queues for AI (RabbitMQ / BullMQ)

Current: The user waits holding an open HTTP connection while Claude generates a response.
Scale: LLM APIs are slow. Under heavy load, HTTP connections would time out. I would push the AI request into a Redis Message Queue (BullMQ). The backend responds instantly with a "Job ID". The frontend then uses WebSockets to listen for when the job finishes and updates the UI.

10. Behavioral Questions (STAR)

Technical skills get you the interview, but behavioral skills pass it. Use SavePoint to answer these standard questions:

1. "Tell me about a time you overcame a difficult technical challenge."

2. "Tell me about a time you had to learn a new technology quickly."

11. Real-World Challenges & Trade-offs

Senior engineers talk about trade-offs. Use these points to show you understand the limitations of your own code:

1. JWT Storage (Security vs Speed)

The Trade-off: I chose to store the JWTs in `localStorage` because it was much faster and simpler to set up for a React SPA. However, I know full well that this exposes the token to Cross-Site Scripting (XSS) attacks. If this was a production app at a real company, I would have set up a reverse proxy and stored the JWT in an `HttpOnly` cookie.

2. NoSQL vs SQL (Flexibility vs Integrity)

The Trade-off: I could have used MongoDB to build this app twice as fast since I wouldn't have to define strict schemas or migrations. However, I chose the harder path of PostgreSQL because video game trackers require intense data integrity (you can't have a review for a game that was deleted). I traded development speed for long-term stability.

3. Client-Side Rendering (SEO vs Interactivity)

The Trade-off: By using React (Vite) as a Single Page Application, the app feels incredibly fast and app-like. However, the initial HTML is completely empty, making it terrible for Search Engine Optimization (SEO). If I needed Google to index the game review pages, I would have used Next.js for Server-Side Rendering (SSR) instead.

13. Production Readiness & Security

Protecting the application against real-world vulnerabilities and managing production state.

1. Rate Limiting & API Protection

The Problem: External APIs like Claude AI and IGDB charge by usage or have strict rate limits. A malicious user could spam the "Recommend" button, bringing down the service.

The Solution: I implemented express-rate-limit middleware on the backend. The AI recommendation route is strictly limited to 5 requests per IP address every 15 minutes. Search routes have a slightly higher limit but are still capped to prevent automated scraping.

2. Advanced Frontend State (React Query vs useEffect)

The Defense: While I used a manual useEffect combined with Axios for the game search, I recognize that manually handling loading, error, and caching states is prone to race conditions. In a large-scale production app, I would use React Query (TanStack Query) or SWR to elegantly handle server-state, automatic retries, and cache invalidation on the client side.

3. Error Tracking & Observability

The Problem: Basic console.log() statements are useless when the backend is running on a cloud server and crashes silently.

The Solution: I discussed integrating a tool like Sentry for production. If an unhandled promise rejection occurs (like a database connection failure), it logs the exact stack trace and alerts the engineering team via Slack, rather than the user just seeing a generic loading spinner forever.
